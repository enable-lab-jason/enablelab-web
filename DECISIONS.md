# Decision log: ENABLE Lab website rebuild

Each step records what was decided, why, and what else was considered.
Date: November 22, 2026.

---

## Step 1. Scope: same content, new presentation

**Decision:** Keep the content of all seven pages of sites.ua.edu/enablelab (home, research projects, lab members, publications, teaching, education & outreach, contact). Change the structure, design and academic features. Add three pages: **News** (moved off the home page), **Join us** (the open Ph.D. position was buried on Contact) and **one page per research project**.
**Why:** You asked for "almost the same" content. The new pages only reorganize content that already existed.

## Step 2. Collecting the content

**Decision:** Read every page of the live site and rebuild the text faithfully from it.
**Constraint:** The tool used to read the site summarizes page text rather than copying it word for word. Facts, names, dates, numbers, links and all 53 citation records were captured exactly. Some sentences are lightly reworded.
**What to do:** If you want any paragraph word for word as before, paste it into the matching file in `content/`.

## Step 3. Platform: static site on GitHub Pages, built by GitHub Actions

**Decision:** A static website generated by a small Python script (`build.py`, using Jinja2 templates) from plain-text YAML files. GitHub Actions builds it and publishes it to GitHub Pages on every change.
**Why:**
- It's free and needs no server, database or WordPress updates.
- Every change is versioned in Git, so you can see who changed what and undo mistakes.
- Content is separate from design: lab members edit `content/*.yml` in the browser and never touch HTML.
- The exact build GitHub runs could be tested end to end here (see Step 10).

**Alternatives considered:**
- *Jekyll / Greene Lab "Lab Website Template"* (recommended in the earlier plan). Its Ruby toolchain could not be installed in this build environment (the RubyGems download was blocked), so a Jekyll site could not be tested here before delivery. Shipping an untested build would risk a broken first deploy. The Python approach keeps the same benefits: data files, automatic deploys and pull-request checks.
- *Hand-written HTML.* Rejected: every news item or new member would mean editing HTML on several pages.
- *Staying on WordPress.* Rejected for this task, which asked for GitHub.

## Step 5. Visual design

- **Colors:** UA crimson (#9E1B32) is the only accent, on white and cool slate grays. A cream-and-serif look and generic card grids were avoided because they read as templates.
- **Type:** Libre Franklin for headings and interface text (the Franklin Gothic family is common in collegiate typography) and Source Serif 4 for reading text, which gives a journal feel. Both load from Google Fonts, with system fallbacks.
- **Signature element:** a biosignal-style waveform (EMG bursts and a gait curve) traced once across the hero when the page loads. It's subject-specific, it's the only decorative animation, and it's switched off for visitors who prefer reduced motion.
- **Layouts follow content type:** projects use figure-plus-text rows; publications use numbered references (the IDs J26, C27 and so on are real identifiers); news and outreach use date timelines.
- **No UA logo file.** Using the university wordmark off university servers normally needs brand approval, so the header uses the lab's own mark and the text "Department of Mechanical Engineering, The University of Alabama". The footer says the site is maintained by the lab.

## Step 6. Academic features added

- Search and filters on Publications; BibTeX for every paper; DOI links where a DOI is known.
- Links between projects and papers (each paper shows its project; each project lists its papers).
- schema.org structured data (ResearchOrganization, Person, ScholarlyArticle list) so search engines understand the lab, the PI and the papers.
- Open Graph tags for link previews, `sitemap.xml`, `robots.txt`, an RSS news feed and a custom 404 page that helps visitors arriving from old links.
- Scholarly profile links (Google Scholar, ORCID, ResearchGate, CV) on the PI profile, Publications page and footer.

## Step 7. Accessibility (WCAG 2.1 AA)

**Decision:** Build to WCAG 2.1 AA, the standard under the DOJ's ADA Title II rule for public universities (compliance date for large public entities extended to April 26, 2027).
**Done:** skip link, keyboard-operable menu and filters, visible focus, alt text on every image, labeled form controls, table headers, reduced-motion support, sufficient color contrast. An automated axe-core audit of all 21 pages found **0 violations**.
**Still needed by a person:** the old site had **no alt text**, and the images could not be viewed during the build. The alt text was written from captions, file names and project titles. Please replace generic text such as "MATHCOUNTS 2024 STEM demo, photo 2" with what each photo shows. Videos should also get captions.

## Step 9. Images and video

**Decision:** At first the site links to the images and video on sites.ua.edu. A one-click GitHub workflow ("Import images from old site") copies them into the repository, and the build then uses the local copies automatically.
**Why:** Images couldn't be downloaded in this build environment. Copying them makes the new site independent of the old one. Files over about 45 MB (possibly the lab video) stay linked to the old site because GitHub rejects files over 100 MB.

## Step 10. Testing before delivery

- The build ran in a clean Python environment with only `requirements.txt` installed, the same way GitHub Actions runs it.
- The link checker (`scripts/check_links.py`, also run on GitHub for every change) found no broken internal links or anchors and no images missing alt text.
- axe-core accessibility audit: 0 violations on 21 pages.
- Browser tests: search, type, year and project filters, the "no results" message, BibTeX toggle, research-area links, news category filters and the mobile menu all work, with no JavaScript errors. No page scrolls sideways at a 390 px phone width.
- Content mistakes produce plain-language build errors (for example "A news item links to publication 'J99', which is not in publications.yml"), and GitHub won't publish a broken build.

## Step 11. Hosting address

**Decision:** Publish at `https://<your-github-username>.github.io/enablelab-website/` first. Optionally move to a UA address (for example `enablelab.ua.edu`) later; that needs a DNS record from UA OIT. The build picks up the address automatically, so no code changes are needed.
